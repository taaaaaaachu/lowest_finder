# RBAC: ロールと権限モデル

## 決定

会員に `super_admin` / `admin` / `user` の1ロール(厳格階層)を持たせ、管理操作を役割で制御する。詳細な非対称性を以下のとおり定める。

- **ロールの起点**: 最初に登録したユーザーが `super_admin`(新規は 1 人目、既存 DB は最古参をマイグレーションで昇格)。
- **管理者は昇格のみ・降格不可**: admin は `user → admin` の昇格だけ可能。降格(罷免)・super_admin の任命・admin/super_admin へのロール変更は一切できない。ロールの自由な付け替えは super_admin のみ。
- **last-super-admin ガード**: システムに super_admin が常に 1 人以上。**削除と罷免(降格)の両方**で「最後の 1 人」を拒否する。片方だけ守ると抜け穴になるため両方に効かせる。
- **削除範囲**: super_admin は全員(自分含む、ガード付き)。admin は一般ユーザーのみ。admin は自分自身を削除できない(削除対象が user に限られるため)。一般ユーザーの自己削除は無し。
- **パスワード**: 本人によるセルフ変更は全ユーザー可(現パスワード要求・自端末のみセッション維持)。管理者リセットは super_admin=全員 / admin=一般ユーザーのみ(現パスワード不要・対象者の全セッションを無効化)。
- **ユーザー削除時のデータ**: グループ・商品はカスケード削除。招待の行は**残す**(`created_by` を SET NULL に変更、`used_by` も SET NULL)——監査履歴を保つため。
- **ロール変更は即時反映**: hooks が毎リクエストで DB からロールを読むため、降格は次のリクエストで有効。ロール変更でのセッション無効化は不要。

## 背景・理由

- Cloudflare Tunnel で公開する家族〜小規模運用で、招待・ユーザー・パスワードの統制を役割で分けたい。単一 enum + 厳格階層が要件を最小の複雑さで満たす。
- 「admin は昇格のみ」は、誤任命の巻き戻しを super_admin に集約して権限を明確にする意図的な非対称。将来の読者が「なぜ admin は降格できないのか」と混乱しないよう明記する。
- last-super-admin ガードを削除と罷免の両方に効かせるのは、どちらか一方だけだと super_admin を 0 にできてしまい、以後誰も昇格できずロック状態になるため。
- 削除時に招待を SET NULL で残すのは、「誰がいつ登録したか」の監査価値を、発行者ユーザー削除後も保つため。

## 帰結

- UI でボタンを出し分けるだけでなく、**サーバー側で必ず権限判定**する(UI 非表示は防御にならない)。
- 管理機能は `/admin/users`・`/admin/invites`(admin+)、セルフのパスワード変更は `/account`(全員)に分離。
- ロール変更・削除の専用監査ログは持たない(招待の created_by/used_by の記録のみ)。必要になれば別途追加。
